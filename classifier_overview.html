Task 1: Machine Learning Challenge¶

Gene classification ML pipeline¶

The pipeline performs binary classification, predicting whether a gene set is involved in the same disease (y=1) or not (y=0). Input features include a binary disease-type indicator (germline=1 and somatic=0), a repeat index from a data augmentation strategy (rep), a 512-dimensional embedding vector (emb_0 to emb_511), a literature co-mention score (sc), and a normalised gene count (num_genes).

2 – Data exploration and preprocessing¶
One of the most important factors in building a good quality Machine Learning model is the data used for training. Therefore, it is essential to explore the data, identify any issues, and apply any preprocessing, as appropriate.


In doing this, it is important to consider the features present within the datasets, which are as follows:


Input features¶
disease:¶
Binary input indicating if, 1 = Disease predominantly driven by germline mutations or 0 = Disease predominantly driven by somatic mutations.


rep:¶
Integer (1–5) indicating the repeat index from a data augmentation strategy (to increase training dataset size).


emb_0 to emb_511:¶
512-dimensional feature vector, Deep learning–derived embedding of publicly available multi-omics data for each gene set.


sc:¶
Literature-based co-mention score derived from in-house computational analysis of PubMed (January 2025). Providing a normalised measure of how frequently genes in a set are mentioned together in the context of the same disease.
Higher values indicate a greater likelihood that the genes are associated with the same disease.


num_genes:¶
Number of genes in the gene set being evaluated, divided by 1000.


Target feature¶
y:¶
Binary target feature, 1 = Genes are involved in the same disease, 0 = Genes are not involved in the same disease.

2.2 – Data exploration and processing overview¶


Shape¶
The shape of both the train and test datasets were examined to ensure that the number of input columns is consistent between sets and that the test set has the correct number of rows required to produce the expected output, formatted correctly.


Column counts for both sets were as expected with one fewer column in the test set because it does not include the target feature ('y') column. Test set row count was also as expected at 1154, the verification output being 1155 because it includes the file header row.




ID ranges¶
ID ranges were examined to ensure that there was no overlap between datasets and that the test set would start at 15411, which was all found to be as expected.




Missing values¶
Missing values can reduce accuracy, create bias and cause other issues within machine learning models so the datasets were examined to identify whether any were present. Fortunately, none were present in either dataset.




Duplicate rows¶
Duplicate rows within each dataset would also affect model accuracy and potentially introduce bias. The only duplicate rows found were in the test data set and as these would have no effect on training and validation, they were included to keep the output file structure unchanged. Duplicate rows between sets (cross-duplicates) would indicate redundancy leakage but none were identified.




Classification distribution¶
Determining the classification distribution of the target feature is important because an imbalanced target feature will introduce bias into the model. The model learns that if it assigns one classification it will be correct a greater proportion of the time so it assigns that classification more frequently.


With that in mind, the training dataset was examined to identify the presence of any such imbalance, and it was found that almost 5x as many genes were not involved in the same disease as those that were. Even if this were representative of a real world distribution, the model would learn to rely on the imbalance in making its predictions, rather than the input features. In this case, a model that guesses 0 every time (i.e. genes not involved in the same disease) will be correct 83% of the time. Therefore, as accuracy is misleading metric, F1 score will be used as the primary evaluation metric instead.




Co-mention scores¶
Co-mention scores were examined to determine whether there were any differences between the datasets, as such differences would prevent the model from being generaliseable. It was found that the scores are all zeros in the test set, meaning that this feature can't be generalised and has no predictive value, so it was dropped from both sets.




Normalised gene counts¶
Distribution of normalised gene counts was also examined to determine whether there was a difference between the datasets. Although the max values from each of the datasets were different, the minimum was the same for both, while the mean and standard deviation values were similar. There are no obvious issues with the normalised gene counts.




Repeat indexes¶
The repeat index column will be removed from the datasets, as it is an artifact of the data augmentation strategy and does not have any biological relevance. This will be done post data split so that indexes can be utilised to stratify the groups during splitting and prevent augmentation leakage, whereby augmented versions of the same data point appear in both the training and test sets.

Model training requires training and validation datasets so an 4:1 split is prepared here, using the train set, stratifying the split according to both repeat index and target feature. This ensures the following:

4 – Model benchmarking and selection¶
An initial StratifiedKFold cross-validation was performed with three classifier models, these being Logistic Regression, Random Forest, and XGBoost, with XGBoost being found to perform the best out of the three (F1 scores: 0.29, 0.49, and 0.84, respectively). Standard hyperparameters were mostly used for this comparison, but all models had random_state set to 42 and weighting to account for class imbalance in the target feature column. Additionally, the Logistic Regression model had max_iter set to 1000 to allow it to converge. The XGBoost model was taken forward for further hyperparameter optimisation and to be used in the final pipeline.






















5 – Model training and validation¶
An XGBoost Classifier model was initialised with a binary:logistic objective, which uses logloss as its tree evaluation metric by default. random_state was set to 42 to control randomness and ensure reproducibility. scale_pos_weight was set to 5, as this was the approximate ratio of class 0 to class 1 in the target feature column, to account for the class imbalance present.


Model evaluation¶
Model performance was assessed with F1 score as the primary evaluation metric. Training and validation logloss curves were plotted to provide an indicator of model overfitting. Hyperparameters were optimised to produce as balanced a model as possible with high F1 score, while limiting overfitting.

# @title 5.1 – Train and test XGBoost classifier model

# Initialise XGBoost Classifier model
# XGBoost performed the best out of the models tested in the benchmarking stage
clf = xgb.XGBClassifier(
    objective="binary:logistic",
    random_state=42,
    scale_pos_weight=5,         # Approximate ratio of class 0 to class 1
    learning_rate=0.02,         # Conservative learning rate to reduce overfitting
    n_estimators=1000,          # Increased number of trees to give model time to improve
    max_depth=3,                # Tree depth limited to prevent overfitting
    min_child_weight=2,         # Minimal data points per leaf, increasing didn't help with overfitting
    subsample=0.6,              # Smaller fraction of training rows sampled per tree, to reduce overfitting
    colsample_bytree=0.8,       # Reducing fraction further had little effect on overfitting
    early_stopping_rounds=10,   # Early stopping to prevent overfitting
)

# Train the model on training data
clf.fit(X_train, y_train,
        eval_set=[(X_train, y_train), (X_val, y_val)],
        verbose=False)

# Retrieve evaluation results
results = clf.evals_result()                    # Retrieve log(loss) values
train_loss = results['validation_0']['logloss'] # Retrieve training log(loss) values
val_loss = results['validation_1']['logloss']   # Retrieve validation log(loss) values

# Plot learning curves

plt.xlabel('Number of Trees')           # X axis label
plt.legend()                            # Figure legend
plt.show()

# Make predictions on validation date
y_pred = clf.predict(X_val)

# Calculate and print evaluation metrics

5.2 – Hyperparameter optimisation and F1 score analysis¶


Learning rate parameters¶
learning_rate and n_estimatorswere first optimised, finding that minimising learning_rate and setting n_estimators to a high value worked best for achieving a high F1 score while preventing overfitting.




Tree structure parameters¶
It was found that increasing max_depth of trees beyond 3 massively increased the difference in logloss between the training and validation sets, indicating overfitting to the training data. Increasing min_child_weight beyond 2 negatively impacted F1 score without improving overfitting. Similarly, gamma was left at 0 for the same reason. subsample and colsample_bytree were set to 0.6 and 0.8, respectively, found to result in the optimal balance between model performance and overfitting.




Regularisation parameters¶
Ultimately, it was determined that regularisation parameters (reg_alpha and reg_lambda) didn't affect model performance enough to be included in the final pipeline. An early_stopping_rounds of 10 was initially included but the model logloss continues to improve each iteration so this was ultimately excluded.




Analysis¶
Although F1 scores for class 0 (0.97) and class 1 (0.86) aren't quite balanced, increasing scale_pos_weight any further would mean that it would no longer represent the distribution present in the dataset. The hyperparameter settings outlined achieved the most balanced outcome between F1 score and overfitting.

# Define embedding dimensions and importance scores lists
emb_dimensions = []

# Iterate over embeddings columns

  if emb_dimension.startswith('emb_'):            # Filter to only embedding features

    emb_dimensions.append(dim_index)              # Appends each index to the emb_dimensions list

sorted_pairs = sorted(zip(emb_dimensions, imp_scores))

# Unzip the sorted pairs back into two separate tuples

6.2 – Feature importance analysis¶
The top 10 most important features are all embeddings, when considering gain in model performance and coverage of the data but normalised gene counts had by far the greatest importance with regards to weight. Weight represents how frequently a feature is used to split a tree, but as normalised gene counts don't appear in the top 10 features for gain or coverage, these splits aren't likely to have a large effect on model performance, and each split covers relatively few data points.


However, it should be noted that there is a very large disparity (almost 600) in weight, meaning that it was used much more frequently than any other feature to make decisions. It was considered that larger gene sets might be more likely to contain genes involved in the same disease, and this might be more frequently used by the model in forming early trees but as previously stated, since it does not have a significant effect on gain or coverage, it isn't likely to pose a massive issue and removing the column entirely resulted in a noteable reduction in overall model performance.


With regards to the embeddings, it was decided to examine their gain scores in more detail, as embedding feature importance varied the most with regards to gains. All embeddings were plotted out to get a general idea of their relative importance and although a small number of dimensions have notably higher importance, gain is distributed across the majority of the 512 dimensions, suggesting the model is drawing on broad biological signal rather than relying on a small number of features.
